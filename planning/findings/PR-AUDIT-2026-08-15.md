## #446 — PHP namespace resolution (head `83b9be4`)

### Upstream implementation (83b9be4)
`collectPhpNamespaces` records unbraced namespace spans + a parser-level count
of `namespace_definition` nodes (`phpNamespaceBlocks`); `resolveEdges` skips
the per-file FQCN import map for multi-block files. Covers: multi-namespace
ambiguity, same-name braced blocks, use-only blocks, single-namespace control.

### Regression found (fixed previously — commit `0a7d97f`)
The guard counts namespace blocks only; the **global scope is never counted**,
so a file mixing a global `use` with namespace blocks still built the per-file
FQCN map and emitted a wrong high-confidence `CALLS @0.9` across the boundary.

| Case | base 043bc68 | 83b9be4 | 0a7d97f |
|---|---|---|---|
| C6 global `use` + block declares own symbol | no wrong edge | **wrong edge @0.9** | no edge |
| C8 block `use` + global declaration | no wrong edge | **wrong edge @0.9** | no edge |
| D global `use` + block + decoy file | none (ambiguous) | **wrong edge @0.9** | none |
| E global `use` + unbraced namespace | no wrong edge | **wrong edge @0.9** | no edge |
| C7 block `use` → global code, no declaration | wrong edge @0.9 | same | same (**pre-existing**) |

**Fix (0a7d97f):** `collectPhpNamespaces` records, on the existing single
walk, whether a top-level `use`/declaration sits in global scope
(`phpMixedScope`); `resolveEdges` skips the FQCN map for such files. Purely
parser-level, no second traversal. 4 new behavioral tests; `declare(strict_types=1)`
positive control proves no over-skip. resolveEdges 88 + queries.php 11 +
patchBuilder.resolution 14 = 113/113 pass; tsc clean.

Branch: `fix/446-namespace-scope-boundary` → fork `0a7d97f`
(https://github.com/Alot1z/Ix-remap/commit/0a7d97f6213e567bcd074ebe7fb41cd32b77e7c3).
Posted on #446 as comment `5303306410`.

## #443 — renamed type imports + default-import guard (head `eab1075`)

### Implementation
Renamed-import fallback in `resolveEdges`: when the provider file's public-name
map misses `binding.imported`, fall back to any symbol in the provider file
(`fileHasSymbol`). `eab1075` added a guard for the literal sentinel `'default'`.

### Regression found (fixed — commit `cba11a3`)
The fallback accepts **any** provider symbol, including class methods. The
`'default'` guard covers only the default-import sentinel; a renamed
`import { Base as LocalBase }` binds to a method `M.Base`, and a renamed type
reference binds to `M.User` — confident 0.9 edges to members that can never be
module exports. Verified by building base vs head:

| Case | base fef671c | eab1075 | fixed cba11a3 |
|---|---|---|---|
| X1 renamed EXTENDS → method `M.Base` | no edge | **wrong edge @0.9** | no edge |
| X2 renamed EXTENDS → exported class | no edge (false negative) | correct edge @0.9 | correct edge |
| X3 renamed REFERENCES → method `M.User` | no edge | **wrong edge @0.9** | no edge |
| X4 non-renamed EXTENDS → method | wrong edge @0.9 | same | same (pre-existing) |

Non-renamed variants (A/C/D/E probes) are identical on base and head — the
legacy stem path already produced the same outcome, so the fallback's *new*
surface is exactly renamed EXTENDS/REFERENCES, where the base emits nothing.

**Fix (cba11a3):** the fallback now requires a **plain (unqualified) qualified
key** (`fileQKeys.get(fp)?.get(imported)?.includes(imported) === true`) instead
of any `fileHasSymbol` match, restricting it to top-level symbols. Methods and
other container'd members can no longer satisfy an import. Two regression tests
(X1/X3); resolveEdges 70/70 pass; tsc clean; fail-before/pass-after verified.

Branch: `fix/443-renamed-import-member-guard` → fork `cba11a3`
(https://github.com/Alot1z/Ix-remap/commit/cba11a3363b1fbe57819381f05490d2f395674cd).

## Cross-PR pattern (elevated finding)

**Import bindings must never resolve to container'd members.** Three PRs in
this chain (#443, #445, and the earlier #446 C7 class) all share one
architectural weak point: a resolver path that matches a *name* against a
provider file's symbol table without requiring the symbol to be at the scope
the name is bound at (module export / top-level / namespace). #443's `'default'`
guard was a sentinel-specific patch of this; the durable fix (plain-qualified-key
requirement) is scope-level and applies uniformly. Recommendation for upstream:
when adding import-resolution paths, require the target qualified key to be
plain (unqualified) unless the semantic explicitly licenses members.

## Third-order sweep (same session) — #446 FQCN index false negative (F-019)

**Regression found:** `phpTypeFqcn`/`ambiguousPhpTypeNames` exclude any PHP
entity carrying a `container`. PHP types (class/interface/trait/enum) can never
be nested, so a container on one is always an inclusive-line-range artifact of
`findEnclosing`: two sibling declarations on the same line (`class A {} class B {}`)
falsely nest B inside A. The FQCN index then drops B, and an import that the
pre-#446 baseline resolved at 0.9 becomes a false negative (NONE).

| Case | base 043bc68 | 83b9be4 / 0a7d97f | fixed f577492 |
|---|---|---|---|
| same-line provider + `use Vendor\Package\B; new B()` | IMPORTS @0.9 | NONE | IMPORTS @0.9 |
| multi-line provider (control) | IMPORTS @0.9 | IMPORTS @0.9 | IMPORTS @0.9 |

**Classification:** regression introduced by #446 (the whole FQCN machinery is
absent in the base; the container exclusion is #446 code). Severity medium —
false negative, narrow trigger (same-line layout), no false positives.

**Fix (fork commit `f577492`, parent `0a7d97f`, branch
`fix/446-namespace-scope-boundary`):** drop the `entity.container` check in
`phpTypeFqcn` and `ambiguousPhpTypeNames` with a comment explaining PHP types
can't nest. Regression tests: same-line positive + multi-line control, both
asserting IMPORTS @0.9 to the provider; fail-before (expected [] to have length
1) and pass-after verified. resolveEdges + queries.php + patchBuilder.resolution
115/115, `tsc --noEmit` clean, `git diff --check` clean.

**Probe-validity note (important):** earlier same-session probes written via
Git-Bash heredocs silently collapsed `\` → `\`, and JS then dropped the unknown
escape (`\P` → `P`), so `use Vendor\B` parsed as a single name `VendorB` — those
probes' resolution outputs were invalid. All conclusions in this section were
re-derived with write_file-written probes (backslashes intact) and verified
against both dists. The span/binary-search audit (P1–P13) found no off-by-one or
scope-classification bug in `collectPhpNamespaces`/`phpNamespaceForNode`; the
only anomalies were the same-line container artifacts, which are pre-existing
(`findEnclosing`, identical on base and head).

**Related:** the second-order sweep's "FQCN path immune by construction" claim
concerned member-binding (false positives); F-019 is a false negative on a
different axis and does not contradict it.

**Conclusion:** the regression propagates into the incremental/cross-batch
index, and `f577492` already fixes every path — the global-index builder
(`buildGlobalResolutionIndex` PHP section), the `resolveEdges` merged builder,
and the `importedPhpType` consumer all share the single `phpTypeFqcn` /

builds the global index per run in memory (`ix-cli/src/cli/commands/ingest.ts`
~1566/1622) — nothing serialized to disk, so no stale-cache path.

**Precise claim (regression attribution):** the same-line container artifact
(`findEnclosing` inclusive line ranges, `B.container = A`) is **pre-existing**
— identical on `043bc68`. #446 introduced the **false negative** by having its
new FQCN indexing treat that artifact's container field as evidence that the
PHP type is nested, and drop it. The fix restores the pre-#446 behavior rather
than changing it.

**Nested-class boundary (invalid PHP `class A { class B {} }`):** tree-sitter
captures no `B` entity, so the FQCN path emits nothing on both `83b9be4` and
`f577492` (identical — not affected by the fix); base emits a file-level
IMPORTS edge for a class that does not exist. Conservative head behavior,
unchanged, not a fix target.
